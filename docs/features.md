# Feature enablement, disablement and change impact

For the opt-in automated package/preload/restart workflow, see [on-premise extension lifecycle](onprem-extension-lifecycle.md). The older `configure` operation retains its manual preload-maintenance boundary.

> Portable configuration: start with [the external deployment setup](environment-portability.md). Addresses in this guide are documentation-only ranges, names are examples, and `/home/OPERATOR` means your controller account. Read measured results as anonymized historical evidence; obtain real values from your own inventory and discovery.

For flexible topology, `ENABLE_BACKUP`, `ENABLE_HAPROXY`, custom extensions and concrete scenarios, use [modular deployment](modular-deployment.md). Legacy Type A component requirements below still apply to that profile.

Only controls consumed by the implementation are documented here. Omission or `false` usually means **do not manage/create**, not **remove what already exists**. All commands use the inventory, verified SSH identities and protected credentials from [installation](installation.md). Package/configuration maintenance and timer changes are separate approved work; never infer that a feature switch makes a live transition safe.

| Feature | Default and supported control | Enable / prerequisites | Disable / consequences | Activation impact and recommendation |
| --- | --- | --- | --- | --- |
| Deployment model | No model required for generic discovery; explicit `postgresql_deployment.mode` for provisioning | `standalone` or `cluster`; qualified major and exact inventory | Choose a different model only for a separately planned deployment; this does not convert or dismantle an existing server | Model change is not an online migration. Select topology for actual availability objectives |
| Routine operation | `postgresql_operation: plan` | Select `provision`, `packages`, `configure`, or identity-gated backup `components` with their specific gates | Return to `plan`; existing state remains | Plan observes; other modes have bounded effects documented below |
| HA and replication | Required by Type A; absent in standalone | Cluster mode with three core nodes, eligible standby, DCS, TLS, backup and fencing prerequisites | No `ha_enabled`/`replication_enabled` flag or automated conversion | Removing HA is a migration; do not stop Patroni while independently starting its PostgreSQL |
| Synchronous replication | No implicit HA policy; explicit `cluster.replication.mode` | `strict_sync` and a valid `synchronous_node_count` | `async` requires count 0 and `acknowledge_async_data_loss: true`; not an automatic DCS update | Changing a live policy requires reviewed DCS maintenance; async can lose acknowledged transactions |
| Read-replica eligibility | Explicit topology lists | Hosts in `topology.replicas` have nofailover/nosync true at fresh creation | Moving to standby list is detected as existing policy mismatch, not applied automatically | Changes affect promotion/durability and need controlled maintenance |
| PgBouncer | Required for Type A routing; absent standalone | Included during HA provisioning | No supported off switch inside Type A | Removal breaks configured router backends; session/transaction pool mode changes need application compatibility review |
| HAProxy/Keepalived/VIP | Required on Type A core; absent standalone | Three core routers, supported subnet/VRRP and approved VIP | Modular profile supports `enable_haproxy: false` and direct endpoints; legacy Type A remains mandatory | Reload/restart or VIP movement can interrupt connections; stage router maintenance |
| Mandatory extensions | `plpgsql` automatically included | Qualified server/control files; normally installed by PostgreSQL | Not removed by desired-list edits | Missing baseline DDL still requires applicable creation admission; retain installed versions |
| Automated extension maintenance | `extension_operation: plan` | `extensions.yml` with identity confirmation; explicit package/repository and restart/interruption flags | Plan makes no changes; omission never drops extensions or unloads libraries | Adds packages/preloads, gates sequential managed restarts, creates and verifies SQL extensions; see the on-premise guide |
| Optional extensions | `postgresql_deployment.extensions: []` | Select catalog/custom names or discover preinstalled native controls; compatible packages and explicit database list | Remove a name from the desired list to stop requesting it; existing extension/package/preload remains | `pgcrypto` needs no preload; statements/kcache/pgaudit need preload activation. No automatic DROP/upgrade |
| Package installation | `postgresql_allow_package_install: false` | True plus exact `postgresql_package_versions`, explicit packages/provision operation and successful simulation | False blocks missing-package installation; installed packages remain | New package role suppresses starts and needrestart restarts; it refuses installed-version/dependency upgrade conflicts. Legacy package helpers are different, separately gated operations |
| Extension creation | `postgresql_allow_extension_create: false` | True with configure identity/hash or admitted provisioning plan | False blocks missing DDL; already-compliant requests are no-ops | Transactional per database; use a secure schema. Failures across multiple databases need inspection rather than DROP rollback |
| Query statistics | Optional `pg_stat_statements`; kcache selects its dependency | Explicit extension list and preload; measure workload overhead/privacy | Removing the requested name does not unload or drop it | Existing preload changes require maintenance restart; detailed tuning is not exposed by this extension workflow |
| Audit logging | Optional `pgaudit` extension | Compatible package/preload plus independently reviewed audit policy | No automation flag turns off an existing audit policy | Extension creation alone does not configure `pgaudit.log` or audit retention. Privileged policy changes need security review |
| TLS | Mandatory HA; mandatory for standalone TCP | HA service-specific `tls_sources`; standalone existing `tls` paths | No HA TLS-disable switch. Empty standalone `listen_address` is local-only on new provision, not a live disable action | Certificate changes/rotation are separately staged; do not weaken verification to handle expiry |
| Standalone TCP | `standalone.listen_address: ''` | Existing assigned IPv4, approved canonical CIDRs, valid cert/key/CA | Empty for a new local-only deployment; completed policy changes are refused | Opening access needs external firewall and application credentials; live change requires maintenance |
| Optional logical backups | Modular `enable_backup: false` | Enable with protected `backup_target_path`; admitted provision or identity-gated `components` | False plus explicit `components` stops only the managed timer, retaining data | Per-database logical snapshots; no PITR, retention deletion or offsite upload; restore qualification required |
| Legacy managed backup transport | No global `backup_enabled`; selected by dedicated HA helper and `backup_repository_host` integration | `backup-platform.yml`, repository variables, pinned pgBackRest and backup trust domain; explicit `backup-platform` maintenance scope | Removing the variable is not a safe live uninstall or archive change | Required recovery capability must remain available; changing repo/keys can make old history unrecoverable |
| External archive integration | HA contract supports tested executable paths when managed repo is not selected | Install/test archive and restore helpers; correct return codes and WAL-path contract | No unattended archive disable; changing handler is coordinated PostgreSQL policy maintenance | Archive failure can exhaust WAL storage. Descriptive destination/RPO fields do not implement a remote repository |
| Legacy pgBackRest backup timer | Not installed by plain model provisioning | `backup-schedule.yml` after backup acceptance; explicit scope `backup-schedule` | No inventory off switch; separately approved stop/disable of `pg-ha-full-backup.timer` stops future scheduled jobs | Does not terminate an already-running job or disable WAL archiving. Disabling requires alternate schedule and age alerts |
| HA monitor timer | Not installed by plain model provisioning | `monitoring.yml`, explicit scope `monitoring`, working application identity and HA/backup services | No inventory off switch; separately approved stop/disable of `pg-ha-monitor.timer` | Stopping creates a detection gap; arrange external monitoring first. Current local-etcd assumption is not qualified on extra database-only nodes |
| Prometheus/exporters/alert delivery | Not implemented | Integrate separately with reviewed least-privilege access and network policy | No project variables for Prometheus address, exporter port or Alertmanager | Local JSON/journald health output is not an external monitoring/alert system |
| Platform storage | `platform_manage_storage: false` | True, exact platform approval, existing VG, reviewed owned/new LV names/size/mount | False skips management; does not unmount/delete existing LVs | May allocate/format new owned resources and mount them. No force-format, shrinking or foreign-LV adoption; capacity operations still need explicit approval |
| Platform networking | `platform_manage_network: false` | True with actual interface, service address/prefix and platform admission | False preserves existing network; does not remove previous aliases | Can affect SSH and service reachability; prefer existing reserved VM addresses and keep console recovery |
| Hosts-file management | `platform_manage_hosts: false` | True with reviewed node/VIP names/addresses and admission | False leaves installed entries | Updates local resolution only, not external DNS; mismatched certificates/names can break connections |
| Firewall management | `platform_manage_firewall: false` | True with approved SSH/client ranges, aligned ports, interface and platform gate | False skips firewall management; does not flush existing rules | Applying policy can block access; verify current source/NAT and out-of-band recovery first |

## Timer control is an explicit operational action

For an approved temporary monitoring pause on the affected HA node, standard systemd commands are:

```bash
sudo systemctl stop pg-ha-monitor.timer
sudo systemctl disable pg-ha-monitor.timer
```

These affect the timer, not an already-running oneshot service. After resolving the cause and verifying alternate coverage, `sudo systemctl enable --now pg-ha-monitor.timer` restores the installed schedule. The analogous backup timer is `pg-ha-full-backup.timer`; pausing it increases backup age and must have an alternative recovery plan. These commands are not proposed routine deployment steps and are not configuration flags. Re-running the corresponding approved installation playbook enables its timer again.

## Settings that are fixed, not feature switches

The current pgBackRest template fixes AES-256-CBC, full retention 2, zst compression and process count 2; the timer performs full backups. No supported S3 bucket, endpoint, region, access-key or immutable-retention variables exist. Repository software capability is not the same as project support. Retention/encryption changes need a reviewed implementation and history/restore migration; editing descriptive inventory text has no effect.

The optional [storage layout](storage-layout.md) supports fresh external WAL and guarded data/backup mount points. It does not relocate existing data/WAL. There are no supported variables to provision tablespaces, turn off HA's TLS/watchdog checks, install a generic Prometheus stack, or remove/reinitialize an existing database. `config_root`/`state_root` are not universal path-relocation switches.
